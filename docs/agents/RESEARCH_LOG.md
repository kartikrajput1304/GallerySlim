#### Trash-aware savings ledger and headroom preflight  `platform-api` · effort M · priority now · fit 4/5
- **What:** Android's MediaStore trash keeps a trashed file on disk until its DATE_EXPIRES time. The docs give the default trash expiry as "typically 30 days" and say expired items are deleted "typically during the next device idle period". So a confirmed createTrashRequest batch frees no space when the user confirms it. Samsung treats the Recycle bin as its own storage category: the Battery and device care > Storage screen lets the user empty it per app. This feature makes GallerySlim's savings figures separate space freed now from space waiting in trash, with dates. It also checks whether there is room to write new copies before a batch starts.
- **Why it fits GallerySlim:** The design doc's planned savings dashboard ("You've freed 12 GB") would report the wrong number on the Galaxy S24, which is 99% full. After confirmation, the originals of the 565 shrinkable JPEGs and the 11 worthwhile H.264 videos stay in trash and keep using space for about 30 days. Meanwhile the new HEIC/HEVC copies use extra space straight away; the design doc already notes that the device needs headroom for both copies. The ledger would record each URI and size from the PendingConfirmScreen batch and show "Freed now: X / In system trash: Y, freed automatically around \<date>". It would read DATE_EXPIRES where MediaStore exposes it and estimate confirm time + 30 days otherwise. It would also check StorageManager.getAllocatableBytes() before an overnight transcode run and size the batch to fit. If space is too short, it would hand off to the system's storage screen with ACTION_MANAGE_STORAGE plus EXTRA_REQUESTED_BYTES. An option to purge early with createDeleteRequest is technically possible, but it conflicts with the settled rule "never createDeleteRequest" (ShrinkViewModel.kt lines 185-186; design doc §6 rules 1 and 4). It should only be listed as a decision for the developer and must never be the default.
- **Expected benefit:** Estimate: removes the gap between what the app says it freed and what Android Settings shows, which is a likely cause of low ratings and of users thinking compression "did nothing". The gap is exactly the bytes trashed in the last ~30 days, so the app can measure it itself. The headroom check stops transcoding from failing on a full disk partway through a batch. *Fact-check corrections: 1) The expected_benefit says "The gap is exactly the bytes trashed in the last ~30 days". "Exactly" is overstated. The docs say the trash expiry is "typically 30 days" and that expired items are deleted "typically during the next device idle period", so items can stay longer than 30 days. #### Better duplicate keeper choice and metadata merge  `pure-kotlin` · effort M · priority next · fit 4/5
- **What:** Competitor duplicate tools do more than delete the extra copies. Apple's Duplicates "Merge" keeps the highest-quality copy, combines captions, keywords and favorites into it, updates albums, and sends the other copies to Recently Deleted. Gemini Photos marks one photo in each set as "Best Result" using edits, favorite status and face detection, and favorites are never selected for deletion. Files by Google puts an "Original" badge on the copy to keep. Samsung's duplicate tool warns that deleting every copy also deletes the original.
- **Why it fits GallerySlim:** GallerySlim currently picks the keeper by "largest pixel count first, newest" (DuplicateFinder.kt lines 18 and 117-123). For near-duplicate bursts at the same resolution, the newest copy is an arbitrary choice, and for exact duplicates it can pick a re-saved copy in a messaging folder over the camera original. Better signals, all of which the app already has or can get cheaply: IS_FAVORITE (already scanned), Laplacian sharpness (already computed by BlurScore), how complete the EXIF is (DateTimeOriginal, GPS, Make/Model), a camera folder over a messaging or download folder, and the earliest capture time. Before trashing the other copies, copy any GPS or date that only they have into a JPEG keeper with ExifInterface (after a createWriteRequest if another app owns it), and apply favorites to the keeper with createFavoriteRequest. Also enforce that every group keeps at least one copy, which avoids the trap Samsung warns about.
- **Expected benefit:** Estimate: fewer wrong keepers and no loss of location or date data when duplicates are removed. No figure is published for this. Measure it as the share of groups where the user changes the suggested keeper. *Fact-check corrections: All five URLs resolve and match their titles, and the competitor-behavior claims are broadly supported. #### Swipe keep/discard triage with a review step and short sessions  `pure-kotlin` · effort M · priority next · fit 3/5
- **What:** Google's own storage manager has a swipe review: swipe right to mark an item for deletion, swipe left to keep it, then tap Review before anything moves to trash. Slidebox made this style popular: swiping up only marks a photo inside the app, and nothing changes in the gallery until the user empties the in-app trash; it also has a full-screen side-by-side compare for similar shots. HCI studies back the approach. Zurn et al. (CHIIR 2019) found that voting on photos is easier and more enjoyable than deleting them, and that deleting can be frustrating. Hellmich and Dinneen (Journal of Documentation 2025) found that deleting happens as a process over time and recommend nudges that show photos or storage use to get people deleting in rounds.
- **Why it fits GallerySlim:** A Compose card stack for the blur list, near-duplicate groups (with side-by-side compare) and the new age/source lanes. Each swipe only adds to or removes from the existing pending set, and the existing PendingConfirmScreen still sends one createTrashRequest dialog for the batch, so the safety model is unchanged. Swiping is undoable until confirmation. Add an optional short session (for example 20 cards) that WorkManager can suggest when free space drops, matching the iterative deletion the 2025 study describes.
- **Expected benefit:** Qualitative evidence only: deciding by vote is reported as less frustrating than deleting (CHIIR 2019, 10 participants), and people report more positive feelings after deleting (JD 2025, 12 participants). Both are small exploratory studies, so treat the effect as an estimate and measure items reviewed per session in the app. *Fact-check corrections: These are wording issues, not refutations. (1) The Google swipe review is not a general feature of Google's storage manager. It sits only in the "Manage your storage with cleanup target" section, a Google One storage-manager flow for users who are over quota. After Review, the user taps Delete and then picks "Move to trash" or "Permanently delete". So the flow can skip trash entirely. (2) Calling right = delete and left = keep "Google's convention" overstates it. It comes from one Google One cleanup flow, not a platform-wide Android standard. (3) "Slidebox made this style popular" is an editorial claim. The TechCrunch article does not support it; it only describes Slidebox's features. (4) The phrase "more positive feelings after deleting" (JD 2025) is supported. The paper (section 4.3.1) says positive affective aspects were experienced "twice as often after the deletion". Note that this comes from interviews with 12 people, not a measured outcome. (5) The 2025 paper does not specifically recommend "short sessions" or "20-card sessions". It recommends customisable random display of photos or storage occupation to encourage starting to delete and deleting in rounds. The session length is the researcher's own design choice.*
- **Risks:** A fast swipe can cause accidental discards. Keep an undo for the last swipe and the review step before the system dialog. Make swipe directions match Google's convention (right = delete, left = keep) or label them clearly. Gestures need accessible alternatives such as buttons and TalkBack actions. Nudge notifications must be opt-in and infrequent to avoid annoying users.

#### Low-quality photo detector with blur false-positive guard  `pure-kotlin` · effort S · priority next · fit 3/5
- **What:** Files by Google's "suggested pictures" card looks for photos that are blurred, low resolution, or too dark or too bright, and it appears only when at least five such images are found. A review of Gemini Photos, which also flags blurred shots, reported false positives on photos that were mostly sky and clouds, and photos of statues and columns misfiled as "Notes". Gemini still asks users to review the clutter it preselects.
- **Why it fits GallerySlim:** GallerySlim flags blur by Laplacian variance below 100 (BlurScore.kt line 35). That method gives low scores to scenes with little texture (sky, snow, plain walls, night shots), which is the failure the Gemini review describes. The app already computes downscaled luma for blur and SSIM, so it can add exposure checks from the same histogram (mean, share of clipped shadows and highlights) and a low-resolution check from the existing width and height. For blur, keep only images where both overall variance and edge density are low, or show low-texture images as "maybe" without selecting them. Show the card only above a minimum count, as Google does, and never preselect items in these categories.
- **Expected benefit:** Estimate: more useful and more trusted cleanup suggestions, with fewer wrongly flagged "blurry" landscapes. The cost is close to zero because the luma buffer already exists. No source gives a precision figure; measure the share of flagged items users dismiss. *Fact-check corrections: No material overstatement. Minor caveats: (1) The MacStories review reports the sky/clouds false positive but says nothing about how Gemini detects blur. Saying it is "the failure the Gemini review describes" for Laplacian variance is the researcher's inference, not something the source shows. That Laplacian variance scores low-texture scenes low is well known, but none of the cited sources covers it. (2) The Files by Google page says users select pictures by hand, with an optional "All items" select. It does not preselect. Only Gemini preselects clutter, which the MacPaw FAQ confirms, so "never preselect" is a design choice, not something Google practises. (3) The MacStories article shows no publication date and the review is old. Treat it as anecdotal evidence about one older product. (4) The "low-resolution check from existing width and height" holds in part. LumaImage carries sourceWidth/sourceHeight (LumaDecoder.kt lines 13-19), but the first 15 fields of MediaItem show no width/height. Whether MediaItem has dimensions would need checking. ## Round 2

### Track A — Compression (angle: lossless and reversible JPEG recompression: Lepton (Dropbox), packJPG, brunsli, JPEG XL lossless transcoding, arithmetic-coded JPEG)

#### Lossless entropy re-optimization that keeps the file a standard JPEG (optimized Huffman tables / progressive scan search), including the protected Ultra HDR photos  `pure-kotlin` · effort M · priority next · fit 3/5
- **What:** jpegtran-style tools rewrite only the entropy-coded data of a JPEG. They compute optimal Huffman tables and can optionally search for the smallest progressive scan configuration (Mozilla's 'jpgcrush' in mozjpeg). The DCT coefficients never change, so every decoded pixel is identical, and the output is still an ordinary JPEG that every viewer, browser and share target opens. The size win is smaller than Lepton's, but it is the only lossless option whose output can replace the gallery file itself.
- **Why it fits GallerySlim:** This is the one technique here that can safely free space on the 351 Ultra HDR photos (38% of the library on the test device), which are skipped today. It re-encodes neither the SDR pixels nor the gain map. The Ultra HDR spec says the primary image's length is found by parsing the JPEG, the gain map is located from that length plus its XMP Item:Length, and the MPF index can serve as an alternative locator. So after re-coding, the app must rewrite the MPF offsets, and also Item:Length if the gain map JPEG is re-coded too. It also helps whenever HEIC conversion is skipped (output more than 90% of input) or the user wants to keep JPEG. Verification is stronger than SSIM: decode the original and the output with the same decoder and require bit-identical pixels, plus an equal gain map through the Android 14+ Gainmap API. A first pass that only counts symbol frequencies gives the exact saving before anything is written, so the app can skip files that are already optimized. Writing the Huffman decode and optimal-table re-encode needs no IDCT and is feasible in pure Kotlin.
- **Expected benefit:** Published lossless savings: 5.42% total (median about 2.4%) with libjpeg jpegtran and 7.16% with mozjpeg's jpegtran on 920 web JPEGs. #### CAMBI no-reference banding guard for HEVC re-encodes  `pure-kotlin` · effort M · priority later · fit 3/5
- **What:** CAMBI (Contrast-aware Multiscale Banding Index; Tandon, Afonso, Sole, Krasula; Netflix/Stanford 2021) is a no-reference banding detector. It pools the worst 30% of pixels, weighted by contrast sensitivity, and samples one frame every 0.5 s. It has only 5 hyperparameters. Netflix reports that CAMBI below about 5 means no visible banding.

If the output's CAMBI is above about 5 and clearly above the source's CAMBI, the app raises the bitrate step or skips the file. That protects the dark or gradient-heavy clips and screen recordings among the 45 H.264 videos. The same check can run on HEIC photo outputs (sky shots) as an extra guard next to the SSIM-family gate.
- **Expected benefit:** In Netflix's 86-encode subjective banding study, CAMBI's correlation with MOS was SROCC -0.923 and PLCC -0.929, against VMAF 0.088 and 0.000 and PSNR -0.202 and -0.271. It does not directly save space; it lets the ladder or quality loop be more aggressive without risking banding (estimate). *Fact-check corrections: The core claims check out against the paper text (arXiv 2102.00079, Tandon/Afonso/Sole/Krasula, Stanford + Netflix, 2021): 2x2 averaging anti-dither LPF, contrast steps k in {1..4}, 5 scales (4k..135p), a 65x65 window, worst 30% pooling, tau_s = 0.5 s, five rows in Table I, 86 encodes / 23 viewers, Table II SROCC -0.923 / PLCC -0.929 (VMAF 0.088 / 0.000, PSNR -0.202 / -0.271), 95% of 2895 statistically significant pairs, "CAMBI < 5 would suggest no visible banding", and an upscale-to-4k / 10-bit assumption that can be adapted. - **Risks:** The paper's version upscales every frame to 4K and assumes a 10-bit, 4K display. On a phone it would have to run at native or lower resolution with re-tuned window size and thresholds, which the paper says requires adapting the bit-depth and upscaling steps. It was validated on AV1/HEVC Netflix content, not on phone camera footage or screen recordings. #### Source-JPEG quality estimation from quantization tables (pre-encode triage)  `pure-kotlin` · effort S · priority next · fit 3/5
- **What:** A JPEG's quantization tables (DQT) can be matched against the IJG/Annex K standard tables scaled to every quality level 1-100. This gives the encoder quality the source was saved at, exactly when the tables are standard and approximately when they are not. Cogranne (2018) describes an exact two-step method and shows that common tools such as the ImageMagick and GIMP heuristics can return wrong values. A 2024 least-squares variant adds goodness-of-fit scores (RMSE, Nash-Sutcliffe efficiency) that flag non-standard tables. IPOL 2022 can recover a table from decoded pixels alone, which detects JPEG history in PNGs or screenshots.
- **Why it fits GallerySlim:** Reading the DQT marker costs almost nothing and needs no pixel decode, so every one of the 565 shrinkable JPEGs could be scored before any HEIC encode. The fit score tells the app when the estimate is unreliable, for example with vendor-specific camera tables, and should fall back to the current loop.

#### DCT-energy complexity features (VCA) for zero-encode, JND-aware bitrate selection  `pure-kotlin` · effort M · priority later · fit 3/5

#### Screen-content classifier using AV1's content-type detection heuristic  `pure-kotlin` · effort S · priority later · fit 3/5

It is not a 'screen-sharing standard' for offline transcoding, so applying it to file re-encoding is an analogy, not a requirement. The spec also says it 'doesn't generate any guarantee' that text will be legible. (4) The app-specific figures (S24 recordings at 36-43 fps, 4.7-8.1 Mbps, a 1.5x multiplier at >=48 fps) cannot be checked from these sources. They are internal claims and need to be confirmed in the codebase or on test clips. (5) Small point: createDefaultFrameDropEffect queues a frame when (T_x - T_lastQueued) is closer to the target interval than (T_(x+1) - T_lastQueued). 'Keeps the frame closest to each target interval' is a fair paraphrase of that. The simple variant rounds n to the nearest integer.*
- **Risks:** Scrolling-heavy or gameplay recordings will look juddery at lower fps, so this must be limited to clips the pre-scan classes as low-motion, and offered as a user choice (for example 'Screen recording - smaller'). FrameDropEffect is @UnstableApi. Audio/video sync and variable-timestamp handling need testing. Originals still only go through the system trash dialog.
- **Sources:**
  - [FrameDropEffect API reference (androidx.media3.effect) (2026)](https://developer.android.com/reference/androidx/media3/effect/FrameDropEffect) — Media3 provides createDefaultFrameDropEffect(targetFrameRate) (timestamp-closest strategy) and createSimpleFrameDropEffect(expected, target) (keep every nth frame); class is @UnstableApi.

#### Edge-based screen-content quality gate (ESIM-style) for lossy screenshot recompression  `pure-kotlin` · effort M · priority next · fit 3/5
- **What:** ESIM (Ni, Ma, Zeng et al., IEEE TIP 2017) is a full-reference quality metric for screen-content images. It compares edge contrast, edge width and edge direction between reference and distorted images and pools by edge width. The authors report it matches human judgments better than several state-of-the-art general IQA metrics on their public SCID database (1,800 distorted images from 40 references, 9 distortion types). The point is that blur and ringing on text edges matter more to viewers than global luma structure does.
- **Why it fits GallerySlim:** Screenshots that go through the lossy HEIC/AVIF verify-and-retry loop are currently gated by downscaled luma SSIM at <=512px. At that scale, small text from a 1080x2340 screenshot is mostly averaged away, so a 0.97 pass can hide unreadable glyphs. For items the screen-content classifier flags, the gate could switch to a full-resolution (or tiled) edge-similarity score computed from Sobel gradients on luma and chroma, while camera photos keep their existing gate. This tightens quality where text is involved without slowing photos down.
- **Expected benefit:** Mainly a quality and safety gain, preventing saves that hurt legibility. Indirectly it may allow lower quality settings on flat UI screenshots, where SSIM tends to be conservative (unquantified estimate). The source gives no numbers comparing it with SSIM on the abstract page, so calibrate on-device before relying on it. *Fact-check corrections: Nothing material is wrong. Minor points: (1) The abstract says the metric agrees better with human perception than "several state-of-the-art" methods. That is a qualitative claim and the abstract gives no numbers. The finding already says this. (2) The sentence "blur/ringing on text edges matters more than global luma structure" is the researcher's reading. The abstract only says that edges are salient features for SCIs; it does not compare blur or ringing on text edges against global luma structure. (3) Everything about the app (512px luma SSIM gate, the 0.97 threshold, the 1080x2340 text loss, chroma 4:2:0 risk, possibly lower quality on flat UI) comes from the researcher or the codebase, not the source. It is untested and should be treated that way. (4) This page was reached only through a summarizing fetch tool that would not give the full abstract word for word. "Publicly available" for SCID was not separately confirmed.*
- **Risks:** I read only the abstract and metadata, not the full paper, so the exact formulas, constants and pooling must come from the paper (DOI 10.1109/TIP.2017.2718185, closed access) and not be guessed. Full-resolution edge maps cost more than 512px SSIM. A simple gradient-magnitude-similarity version would be easier but is a different, unvalidated metric. Chroma 4:2:0 damage to colored text may need a separate chroma check.
- **Sources:**
  - [ESIM: Edge Similarity for Screen Content Image Quality Assessment (IEEE TIP 26(10):4818-4831, 2017) (2017)](https://scholars.cityu.edu.hk/en/publications/esim-edge-similarity-for-screen-content-image-quality-assessment/) — Full-reference SCI metric built on edge contrast, width and direction with edge-width pooling; SCID database of 1,800 distorted SCIs from 40 references; claimed better HVS consistency than multiple state-of-the-art IQA methods.

#### Matched-frame video spot check before replacing an H.264 original  `platform-api` · effort M · priority next · fit 4/5
- **What:** For each candidate video, GallerySlim pulls the same handful of timestamps (for example 10%, 30%, 50%, 70%, 90%) from source and HEVC output with MediaMetadataRetriever.getScaledFrameAtTime(..., OPTION_CLOSEST, ...). It shows them in the same A/B compare viewer and computes the app's existing luma SSIM on those frame pairs as a coarse, clearly labelled sanity signal. This gives a preview of quality loss for video, which today ships with no on-device quality check at all.
- **Why it fits GallerySlim:** The pipeline admits there is no on-device video metric (VMAF not feasible). The S24 data shows where risk concentrates: screen recordings at 1080x2340 and 36-43 fps carry fine text, and HEVC at a capped bitrate can smear it. A frame-pair check lets the user see text sharpness before trashing the H.264 original. A low frame SSIM, for example below the photo Balanced threshold, can trigger an automatic 'retry at the next ladder rung' or a 'You decide' badge instead of a silent replace. It only needs to run on the 11 videos with meaningful savings, so cost is small.
- **Expected benefit:** Catches obviously bad encodes, such as smeared text in screen recordings or banding in dark scenes, before the original leaves. It is not a perceptual video score: temporal artifacts are invisible to it, and any quantitative threshold would be a project-chosen estimate that needs on-device calibration. *Fact-check corrections: The cited sources support only the narrow API and metric claims. The rest is the project's own reasoning and has no external support. (1) The MediaMetadataRetriever reference confirms that getScaledFrameAtTime(long timeUs, int option, int dstWidth, int dstHeight[, BitmapParams]) "Retrieve[s] a video frame near a given timestamp scaled to a desired size". The finding's claim that "cost is small" does not account for this, since each non-keyframe timestamp needs extra decoding. It does not show that SSIM detects smeared text in HEVC screen recordings or banding in dark scenes. Those specific benefits come from the project, not from the source. (3) No source supports the app-specific details. There are no fabricated numbers attributed to the sources.*

- **Sources:**

#### Session receipt with one-tap 'Undo this run' via MediaStore untrash  `platform-api` · effort M · priority next · fit 4/5
- **What:** Each cleanup or conversion run produces a receipt: what was trashed, what replaced it, and the bytes freed. - **Why it fits GallerySlim:** The app already routes originals through the system trash, but recovery today means the user finds them in Samsung Gallery's trash, one by one, possibly mixed with unrelated deletions. The API reference also notes that apps targeting Android 16 (Baklava) can send at most 2000 URIs per request, so batch restores and trashes must be chunked.
